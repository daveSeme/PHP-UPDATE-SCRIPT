Vulnerability notes

CVE-2026-109618

Remote code execution via OOM corruption

The supplied advisory describes an out-of-memory (OOM) corruption issue. Under vulnerable conditions, memory corruption can affect the integrity of a running process and may create a path to remote code execution.

Action: identify affected PHP installations and deploy the appropriate fixed build.

CVE-2026-109619

Remote code execution via stale global state

The supplied advisory describes a stale-global-state issue. Unexpected or outdated internal state can cause unsafe behaviour in a vulnerable process, potentially creating a route to code execution.

Action: check the affected release information and update PHP rather than relying on application-level workarounds.

Immediate response checklist

  • Inventory all servers, containers, scheduled jobs, and applications that run PHP.
  • Record the PHP version, architecture, thread-safety mode, extensions, and web-server integration.
  • Prioritize internet-facing web applications and any systems running an affected build.
  • Patch from official PHP distribution sources after validating the correct package for your environment.
  • Monitor PHP worker activity, web-server logs, process launches, unexpected outbound connections, and unusual file changes.
  • If compromise is suspected, preserve relevant logs and evidence, isolate the system according to your incident-response plan, and investigate before returning it to service.
  • If an exposed system cannot be patched promptly, consider taking it offline or restricting access according to business continuity and incident-response procedures.
  • Document the installed and target versions, change approval, test results, deployment time, and rollback decision.
Patch first; mitigations are temporary.

Configuration changes and traffic restrictions can reduce exposure, but they should not be treated as equivalent to installing the official security fix. Do not apply unverified mitigation commands without checking the exact PHP advisory and assessing their impact.

Section 02 / Technical implementation

How to upgrade PHP safely on Windows Server + IIS

Use this runbook when PHP runs behind IIS through FastCGI. The examples assume an existing PHP 8.2 installation, potentially used by a Yii or other custom application. Adjust paths and configuration to match your actual server.

Do not replace PHP blindly in production.

Confirm your installed PHP version, x64/x86 architecture, Non-Thread-Safe (NTS) or Thread-Safe (TS) build, loaded extensions, FastCGI executable path, and application requirements first. For a typical IIS FastCGI setup, an NTS build is commonly used, but verify your existing configuration rather than assuming.

Confirm the current PHP runtime

Open PowerShell on the server and run the following. If PHP is not on your PATH, use the full path to your current executable. 

php -v
php --ini
php -m

Record the PHP version, loaded configuration file, extensions, and relevant application dependencies. Also inspect the IIS FastCGI settings to find the actual php-cgi.exe path; the command-line PHP binary and IIS runtime may differ.

Back up the application and server configuration

  • Back up the application files and verify that the backup can be restored.
  • Back up uploaded files, application configuration, and secrets using your approved secure process.
  • Back up the current PHP directory and php.ini.
  • Export or document the IIS site, handler mappings, and FastCGI configuration.
  • Ensure you have a tested database backup if the deployment or application migration could affect data.

Store backups outside the directory being replaced and restrict access to configuration files that contain credentials.

Download the appropriate fixed PHP build

Use the official PHP for Windows download page. Select the correct branch and package for your server's architecture and IIS integration. Do not assume that every ZIP package is interchangeable.

Official PHP 8.2 Windows downloads
PHP 8.2.35 change log

Verify the exact release and its authenticity using the information provided by the official distribution source. If you remain on PHP 8.2, confirm that the target release is actually available and appropriate for your support situation.

Install side-by-side instead of overwriting immediately

A side-by-side directory makes validation and rollback easier. For example, your existing layout might look like this: 

C:\PHP\8.2.27\
C:\PHP\8.2.35\
C:\Sites\YourApplication\

These paths are examples, not a claim about your server's current configuration. Extract the new package to its own directory and keep the old installation intact until the new runtime has passed testing.

Prepare and review the new php.ini

Use the new distribution's recommended configuration template as a starting point. Compare it with your current configuration and migrate only the settings and extensions your application actually needs.

Review settings such as:

extension_dir
date.timezone
memory_limit
upload_max_filesize
post_max_size
max_execution_time
error_log
display_errors
log_errors

Check every required extension against the new PHP build. Extension DLLs must match the PHP version, architecture, and thread-safety mode. Do not copy old extension DLLs into the new installation without verifying compatibility.

Production security

Keep detailed error logging enabled, but normally disable displaying raw PHP errors to public visitors. Never expose secrets or sensitive stack traces in production responses.

Update the IIS FastCGI executable path

In IIS Manager, inspect the site's Handler Mappings and the server's FastCGI Application settings. Update the PHP handler and FastCGI executable to the new php-cgi.exe path, keeping the existing configuration documented.

Typical example of the intended path change:

Old: C:\PHP\8.2.27\php-cgi.exe
New: C:\PHP\8.2.35\php-cgi.exe

Do not blindly create a new handler or delete existing mappings. Check whether the site uses a server-level or site-level configuration, and ensure IIS points to the same PHP build you intend to test.

Restart the relevant services during the change window

Schedule a maintenance window where required. Restart or recycle the affected application pool and confirm that FastCGI workers launch correctly. If a service restart is needed, use your normal operational procedure and assess the impact on other IIS sites before restarting IIS globally.

Watch the Windows Event Viewer, IIS logs, PHP error log, and application logs immediately after the change.

Verify the live runtime, not only the CLI

Run php -v for the command-line version, then verify the PHP version actually serving web requests. If you temporarily use a diagnostic PHP page, restrict access to it, avoid exposing full configuration details, and remove it immediately after testing.

Confirm the reported version, loaded configuration, extension availability, and expected application behaviour. A successful command-line test alone does not prove IIS is using the updated executable.

Test the application and its critical workflows

  • Sign-in, sign-out, session handling, and access control.
  • Database connectivity and key read/write operations.
  • File uploads, downloads, generated reports, and background jobs.
  • Scheduled tasks, mail delivery, API endpoints, and integrations.
  • Yii framework bootstrapping, Composer dependencies, and application-specific features where applicable.
  • Application logs, PHP warnings, response times, and IIS error rates.

Run these checks in staging before production whenever possible. Confirm the application's supported PHP range and test any required Composer dependency checks in the project's normal deployment environment.

Apply ongoing PHP and application hardening

  • Keep PHP, the operating system, IIS, dependencies, and application framework patched.
  • Remove unused extensions and sample scripts.
  • Restrict filesystem write permissions and protect configuration files.
  • Keep secrets outside public web roots and restrict administrative access.
  • Monitor PHP worker behaviour, IIS logs, file changes, and outbound traffic.
  • Use a supported PHP branch and plan upgrades before end of life.

Rollback carefully if validation fails

If the new build causes a serious regression, follow the approved rollback plan: restore the previous FastCGI path and handler settings, restore the prior configuration as appropriate, recycle the application pool, and retest the application.

Rollback is not a security fix.

Returning to a vulnerable PHP build reintroduces the exposure. Use rollback only as a controlled temporary recovery step, restrict exposure as necessary, and arrange a prompt return to a patched build. Investigate the failure before retrying.

Common upgrade problems

HTTP 500 after upgrade

Inspect the IIS logs, Windows Event Viewer, FastCGI configuration, PHP error log, and the application's own logs. Check for a missing extension, invalid configuration directive, permissions issue, or incompatible dependency.

“Unable to load dynamic library”

Verify the extension DLL exists, extension_dir is correct, required dependencies are present, and the DLL matches the PHP version, architecture, and thread-safety build.

CLI is updated but IIS is not

The system PATH may point to the new CLI while IIS still points to the old php-cgi.exe. Review FastCGI Application settings and the PHP handler mapping for the affected site.

Application or framework regression

Check the application's supported PHP versions, Composer constraints, framework compatibility, deprecation notices, and integration tests. Reproduce the issue in staging before changing production settings.

WordPress guidance and the general lesson

WordPress recommends keeping PHP current, checking compatibility with the site and its extensions, and backing up before making changes. Those are useful general maintenance principles for PHP applications.

However, WordPress-specific version recommendations and plugin compatibility checks do not automatically apply to a Yii or custom PHP application. For those systems, confirm the PHP requirements of the actual framework, Composer packages, extensions, and application code.
